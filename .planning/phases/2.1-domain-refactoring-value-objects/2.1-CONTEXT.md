# Phase 2.1: Domain Refactoring (Value Objects & DTOs) - Context

## Decisões Técnicas & Arquiteturais

### 1. Promoção de Primitivos a Value Objects
- **Decisão:** Todos os inputs fundamentais do sistema (Topic, KnowledgeLevel, FocusTime, StudyDays) serão Value Objects imutáveis (`dataclass(frozen=True)`).
- **Racional:** Garante que dados inválidos nunca entrem no domínio do sistema. Centraliza a lógica de validação e evita repetição de código (`validate_topic` sendo chamado em múltiplos lugares).

### 2. Encapsulamento de Dicionários Externos
- **Decisão:** Criar `FirebaseUserDTO` para lidar com a estrutura "solta" do Firebase Admin SDK.
- **Racional:** Melhora a legibilidade e previne erros de `KeyError` ou falta de tipagem em `models/session.py`.

### 3. XML Serialization
- **Decisão:** O método de serialização XML será encapsulado na classe `Prompt` (ex: `Prompt.to_xml()`).
- **Racional:** Embora tenha sido sugerido colocar a serialização em `models/guide.py`, manter o formato do prompt dentro do próprio objeto de Prompt segue o princípio de Alta Coesão. O `Guide` apenas solicita a representação necessária para a IA.

### 4. Gestão de IDs
- **Decisão:** Criar Value Objects específicos para `UserId`, `GuideId` e `Username`.
- **Racional:** Evita confusão entre strings genéricas e identificadores específicos, facilitando futuras migrações ou mudanças de formato de ID.

## Riscos Identificados
- **Breaking Changes:** Como muitos componentes dependem de `dict`, a refatoração será feita em ondas para garantir que a suite de testes (agora robusta após Phase 1 e 2) pegue qualquer regressão.
